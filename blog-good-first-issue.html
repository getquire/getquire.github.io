What a good first issue actually looks like

Most issues labelled good first issue are unscoped work nobody wanted. We rewrote all 62 of ours to name a file, a done condition, and a reviewer who agreed in advance.

RBRita Ben-Ari · Maintainer, core
13 May 2026

We had 62 issues labelled good first issue. Eleven had been open for over a year. Four had a first-time contributor start work and go quiet, which is the outcome that should bother a project most, because that person tried once and will not try again.

Reading them together, the pattern was obvious and slightly embarrassing: most were not first issues at all. They were things a maintainer did not want to do, labelled optimistically. "Improve error messages" is not a task. It is a research project with a friendly name.

The four things a first issue needs

  • A file. Naming the file, ideally the function, removes the single largest cost for a newcomer, which is not writing the code — it is finding where the code lives in a repository they have never seen.
  • A done condition. Something checkable. "This test passes", "this command prints X", "this parse warning appears for the attached document". If the maintainer cannot state it, the issue is not ready for anybody, first-timer or not.
  • A named reviewer who has already agreed. Not a rota, not a team. A person who said yes before the issue was labelled. Waiting two weeks for a review on your first contribution is how a contributor stops being one.
  • An honest size. We write the number of lines we think it is. Being wrong about that is fine and useful; being silent about it means the contributor discovers the scope halfway through an evening they had set aside.
An issue that only makes sense to somebody who already knows the codebase is not a first issue. It is a note to yourself with a label on it.

What the rewrite did

Of 62 issues: 24 were rewritten and kept, 31 were closed or relabelled as ordinary work, and 7 turned out to be already fixed. The label went from a graveyard to a list of two dozen real tasks, which is a smaller number that means something.

The review-time row is doing most of the work in that table. Everything else we changed was about the issue text; the change that moved contribution volume most was a person agreeing in advance to look at the result quickly.

The kinds of task that work

Concrete, bounded, and touching a part of the system where being wrong is visible immediately:

  • A date format for a locale we do not parse yet — a table entry, a test case, and a document in the fixtures.
  • A parser failing on one attached document, with the expected output stated.
  • A flag that exists in one command and not its sibling.
  • A documentation page that is wrong in a specific way, with the correct behaviour described.

The kinds that never work, no matter how well-meant: anything touching the retrieval ranking, anything requiring a judgement call about output format, anything whose test would take longer to write than the fix, and anything phrased as "investigate".

The part that is not about issues

A first contribution is mostly a social event and only partly a technical one. The commit is small. What decides whether the person comes back is whether anything happened afterwards: a review within a day, a merge, a line in the release notes with their name in it, and someone saying which bug it fixed for real users.

That is not scalable if a project treats it as a chore. It is entirely sustainable at twenty-four issues, which is the other argument for having fewer of them.

The labelled issues live in github.com/getquire/quire. If one of them is missing a file, a done condition or a reviewer, that is a bug in the issue and worth saying so.
