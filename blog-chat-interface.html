We deleted our chat interface

Usage tripled in the quarter after we removed it. A conversation is a bad container for work that has to be reviewed, cited and repeated — and a terminal turns out to be a very good one.

ATAnaïs Tremblay · Maintainer, product
8 July 2026

For eighteen months the first thing you saw after indexing a corpus was a message box. It was the obvious design, it demoed beautifully, and the numbers underneath it were bad in a way that took us a long time to read correctly.

Sessions were short. Most were a single question, one answer, no follow-up — which we initially read as success. It was not. The follow-ups were happening; they were just happening in a fresh session, with the question retyped from scratch, because nobody could find the earlier one again.

What a conversation is bad at

  • Re-running. The most common real workflow is asking the same question every month against a changed corpus. In a chat log, that means scrolling to find what you asked in April and copying it. There is no other affordance.
  • Reviewing. A colleague needs to check whether the answer is supported. A transcript containing eleven exchanges, four of which were dead ends, is a bad artefact to hand someone.
  • Diffing. "Has this changed since last quarter" is the question underneath half of all the others, and two chat sessions cannot be compared.
  • Scripting. Nobody can put a chat box in a Makefile.
  • Being wrong usefully. When an answer is wrong, the useful next step is inspecting the retrieval, not rephrasing the question. A message box only offers rephrasing, so that is what people did — three times on average, and then they gave up.
The interface taught people that a bad answer was their fault for asking badly. It almost never was.

What replaced it

A command. One question in, one answer out, with citations, exit code zero or non-zero depending on whether the system was willing to answer at all. Queries live in files. Files live in the repository next to everything else, get reviewed in pull requests, get run on a schedule, and produce output that can be diffed against the last run.

The change was not really about the terminal. It was about making a question a durable object rather than an event. Once the question is a file, everything people were trying to do awkwardly in chat becomes ordinary: version it, share it, parameterise it, run it over a different corpus, put it in CI and fail the build when the answer changes.

The re-run figure is the one that mattered. Two thirds of all usage is asking a question that was asked before, which is a workload a conversation actively obstructs and a file makes trivial.

What we lost

Real costs, stated plainly. Exploration got worse: chat was better for poking at an unfamiliar corpus with vague questions, and we have not fully replaced that. Onboarding is harder, because a message box needs no explanation and a command has flags. And a small group of users left, which is the honest cost of removing something people were using.

We kept one piece of the old design: an interactive mode that is explicitly a scratchpad, and every question asked in it can be written out to a file with one key. Exploration happens there; anything worth keeping graduates into the repository.

The general version

Chat is a default rather than a decision. It is what an interface becomes when nobody has decided what the work actually is. For work that gets reviewed, repeated and cited, the durable artefact is the point, and the conversation was the wrapping paper we kept mistaking for the gift.

The interactive scratchpad is quire ask -i. Everything it does, the non-interactive form does too, which is deliberate: nothing is reachable only by typing at a prompt.
